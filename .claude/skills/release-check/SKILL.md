# Release check

A push to `main` deploys the site (`.github/workflows/deploy.yml`), so merging is the one step here that reaches real users. This skill turns "it passes on my machine" into "it will pass in CI", and doesn't call the release done until the deploy run has succeeded.

The owner reviews every change: never commit, push or merge without their OK (`CLAUDE.md`).

## 1. Preflight — the git side

From the repo root, on the feature branch:

```bash
.claude/skills/release-check/scripts/preflight.sh
```

It checks: on a feature branch, clean tree, in sync with `origin/<branch>`, `main` fast-forwards to it, no Codex copies or local secrets tracked, and it prints any `package.json` changes against `main`. Each line is `PASS`, `FAIL` or `NOTE`; it exits non-zero on any `FAIL`.

A `FAIL` stops the release. Report it with the fix from [references/checks.md](references/checks.md) — don't fix it yourself unless it's mechanical and the owner agrees (pushing an unpushed branch is fine to offer; rebasing onto a moved `main` is their call).

## 2. CI mirror — the fragile step

```bash
.claude/skills/release-check/scripts/ci-mirror.sh
```

It runs exactly what CI runs — `npm ci`, `npm run check`, `npm run build` — on the committed `HEAD` in a throwaway worktree, then removes it. Why not just `npm run check` here: your `node_modules` has grown over time and may hold packages the lockfile doesn't, so a local check can pass while CI's clean install fails. Requirements are in [scripts/README.md](scripts/README.md).

It takes a minute or two; run it in the background if your harness allows, and read its last line: `PASS  CI mirror …` or `FAIL  CI mirror failed at: <step>`.

## 3. Report and ask

Reply with one table — every check, PASS / FAIL / NOTE, and the evidence (counts, test totals, the bundle size from the build) — then:

- If anything failed: what to fix, and stop.
- If `package.json` changed: list each added or moved dependency and ask the owner to approve it — `CLAUDE.md` requires that before any new dependency ships.
- If all passed: ask the owner to approve the merge, naming the branch, the number of commits, and that it will deploy.

Stop here and wait. A release check that merges on its own is a deploy nobody approved.

## 4. Merge — only after the owner says yes

`main` is fast-forwarded, never merge-committed, so the deployed commit is the one you checked:

```bash
git push origin HEAD:main
git fetch origin && git branch -f main origin/main
```

If the push is rejected, `main` moved since preflight — stop and run the check again from step 1.

## 5. Watch the deploy — done means deployed

Find the deploy run for the commit you pushed and wait for it:

```bash
gh run list --branch main --workflow "Deploy to GitHub Pages" --limit 5 --json databaseId,headSha,status
gh run watch <databaseId> --exit-status
```

Use the run whose `headSha` is the commit you pushed — an older run may still be listed. Watching takes a few minutes; run it in the background if you can.

Done when that run's conclusion is `success`. Then report the commit, the run's conclusion and the site URL (`gh api repos/{owner}/{repo}/pages --jq .html_url`). If it failed, show `gh run view <id> --log-failed` and say the site still serves the previous version.

## Gotchas

- `npm warn allow-scripts … npm approve-scripts` during `npm ci` is expected with npm 12 and harmless here. Don't approve scripts to make it go away — that changes what installs are allowed to run, which a release check must never do.
- `AGENTS.md`, `.agents/` and `.codex/` are Codex copies regenerated by the ChatGPT app. They're gitignored; if one ever shows as tracked, that's a FAIL, not something to commit.
- The CI mirror checks the **committed** `HEAD`. Uncommitted work isn't in it — which is why preflight demands a clean tree first.
- Run the scripts from the main checkout, not from inside another worktree.
